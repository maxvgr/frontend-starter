# Backend integration

Информация для backend-разработчиков по интеграции готовой frontend-вёрстки с серверной частью.

Backend получает собранную вёрстку с готовыми HTML-страницами, CSS и JavaScript-файлами.

При интеграции желательно сохранять существующую HTML-структуру, классы и `data-*` атрибуты, так как они могут использоваться frontend-логикой и стилями.

---

# Общие правила

При интеграции не рекомендуется без необходимости:

- переименовывать существующие CSS-классы;
- удалять `data-*` атрибуты;
- менять структуру интерактивных компонентов;
- переносить элементы между контейнерами, если от структуры зависит JavaScript;
- удалять `aria-*` атрибуты;
- изменять `name` полей форм без соответствующего изменения frontend.

Если структура компонента должна существенно измениться, желательно сначала проверить связанную с ним frontend-логику.

---

# Формы

## Общая информация

Формы, подключённые к общей frontend-логике, используют класс:

```html
<form class="form form-custom"></form>
```

В зависимости от проекта frontend может отвечать за:

- клиентскую валидацию;
- маски полей;
- обязательное согласие на обработку персональных данных;
- блокировку кнопки отправки;
- отображение ошибок;
- открытие и закрытие модальных окон;
- отображение успешной отправки.

Backend всегда должен повторно проверять входящие данные независимо от клиентской проверки.

Frontend-валидация не заменяет серверную.

---

# Клиентская валидация

Для включения общей клиентской валидации форма может использовать:

```html
data-validation
```

Поля, которые должны проверяться frontend:

```html
data-validate
```

Пример:

```html
<form class="form form-custom" data-validation>
  <div class="form__field" data-field>
    <input
      type="email"
      name="user_email"
      required
      data-validate
      data-error-required="Укажите email"
      data-error-format="Неверный формат email"
    />
  </div>
</form>
```

Backend должен самостоятельно проверять:

- обязательность полей;
- формат данных;
- допустимую длину;
- корректность email и телефона;
- допустимые значения select / radio / checkbox;
- загруженные файлы;
- любые бизнес-правила проекта.

---

# Согласие на обработку данных

Обязательные checkbox могут быть помечены:

```html
data-privacy
```

Пример:

```html
<input type="checkbox" name="privacy" data-privacy required />
```

Frontend может блокировать кнопку отправки до принятия обязательного согласия.

Backend должен повторно проверить наличие обязательного согласия.

---

# Отправка формы

Frontend по умолчанию не должен определять способ серверной обработки формы.

Backend может использовать:

- обычную HTML-отправку;
- AJAX;
- API;
- CMS;
- CRM.

Для обычной отправки форме можно добавить:

```html
action="/api/form/"
method="post"
```

При этом рекомендуется сохранять существующие frontend-классы и `data-*` атрибуты.

---

# AJAX и успешная отправка

Если форма отправляется через AJAX, после подтверждения успешной обработки данных сервером frontend может быть уведомлён событием:

```js
window.dispatchEvent(
  new CustomEvent("formSuccess", {
    detail: { form },
  }),
);
```

где `form` — DOM-элемент успешно отправленной формы.

Пример:

```js
const form = document.querySelector(".form-custom");

fetch("/api/form/", {
  method: "POST",
  body: new FormData(form),
})
  .then((response) => {
    if (!response.ok) {
      throw new Error("Ошибка отправки формы");
    }

    return response.json();
  })
  .then(() => {
    window.dispatchEvent(
      new CustomEvent("formSuccess", {
        detail: { form },
      }),
    );
  });
```

Событие `formSuccess` должно вызываться только после подтверждения успешной обработки данных сервером.

Не следует вызывать его сразу после начала HTTP-запроса.

---

# Модальное окно успешной отправки

Форма может указывать модальное окно, которое необходимо открыть после успешной отправки:

```html
data-success-modal="success"
```

Пример:

```html
<form
  class="form form-custom"
  data-validation
  data-success-modal="success"
>
</form>
```

При необходимости имя модального окна можно передать непосредственно в событии:

```js
window.dispatchEvent(
  new CustomEvent("formSuccess", {
    detail: {
      form,
      successModal: "success",
    },
  }),
);
```

# Серверные ошибки

Frontend может отображать собственные ошибки клиентской валидации.

Обработка серверных ошибок отдельных полей зависит от конкретного проекта.

Например, сервер может возвращать:

```json
{
  "errors": {
    "user_email": "Некорректный адрес электронной почты"
  }
}
```

Если проекту необходимо автоматически показывать серверные ошибки около соответствующих полей, формат ответа API и frontend-обработку необходимо согласовать отдельно.

---

# Безопасность форм

На стороне backend необходимо реализовать необходимые для проекта меры защиты:

- серверную валидацию;
- CSRF-защиту;
- CAPTCHA / anti-spam;
- защиту от частых повторных запросов;
- проверку загружаемых файлов;
- логирование ошибок;
- безопасную отправку писем;
- безопасную передачу данных в CRM / CMS.

Наличие клиентской проверки не является защитой от прямого запроса к серверу.

---

# CAPTCHA

Если в тестовой вёрстке используется CAPTCHA-заглушка, она не должна считаться production-защитой.

Настоящая CAPTCHA / anti-spam проверка должна выполняться сервером.

Перед production тестовая заглушка должна быть заменена реальным механизмом проекта.

---

# Имена полей

Backend должен ориентироваться на фактический атрибут:

```html
name=""
```

конкретного поля.

Не следует переименовывать поля только на backend без соответствующего изменения HTML.

Желательно заранее согласовать единый набор имён для одинаковых по смыслу полей:

```text
user_name
user_phone
user_email
user_message
privacy
marketing
```

Конкретный проект может использовать другой набор.

---

# Внешние API

API-ключи, токены и другие параметры внешних сервисов желательно получать из конфигурации проекта.

Не следует хранить приватные серверные ключи непосредственно во frontend-коде.

Следует учитывать, что ключи браузерных JavaScript API обычно видны пользователю через HTML и Network.

Для таких ключей необходимо использовать ограничения провайдера:

- разрешённые домены;
- допустимые API;
- квоты;
- другие доступные ограничения.

---

# Динамический контент из CMS

При выводе данных из CMS желательно сохранять существующую структуру компонентов.

Динамическими обычно являются:

- тексты;
- изображения;
- ссылки;
- карточки;
- документы;
- контактные данные;
- пункты меню;
- элементы списков.

При генерации повторяющихся элементов необходимо сохранять ожидаемые классы, атрибуты и вложенность.

---

# Что обязательно проверить после интеграции

После подключения backend необходимо проверить:

- открытие и закрытие модальных окон;
- работу мобильного меню;
- формы;
- валидацию;
- CAPTCHA;
- успешную отправку;
- сообщения об ошибках;
- слайдеры;
- вкладки;
- аккордеоны;
- галереи;
- динамические списки;
- внешние API;
- адаптив;
- отсутствие ошибок в Console.
